Key Finding: Rewrite vs. Iterate

The current codebase is ~2,050 lines of src across 13 modules. Of those, ~40% is ISPAD-specific hardcoding that the redesign deletes. The redesign proposes 15 new/modified files touching every module except evaluate.py. At this scale, iterative migration and a fresh start converge to nearly the same effort — both require rewriting ~1,200 lines and adding ~800 new ones. The deciding factor is whether the existing seams are worth preserving or whether they actively hinder the target architecture. This report evaluates that.

Top Recommendation: Fresh Start

All 5 candidates together touch every module in the codebase. The current architecture has:

  • • No real seams — modules are serial, not pluggable
  • • ~40% ISPAD-specific hardcoding that must be deleted
  • • Two incompatible LLM providers with no abstraction
  • • Notebook-driven orchestration — no programmatic pipeline
  • • No tests for vector, retrieval, or generation layers
  • • Dead code (KVStore L3 paths, atomic extraction notebook)

The only modules with genuine reuse value are the data models (PageContent, SemanticChunk, ChunkMetadata — though all need schema changes) and some extraction logic from pdf_extractor.py (172 lines of clean PyMuPDF wrapping).

Verdict: Start fresh in a new directory. Port the ~300 lines of reusable extraction logic. Build the new architecture from the redesign plan with proper seams from day one. The iterative path would require modifying every file anyway, plus carrying the cognitive overhead of "which parts are old vs. new."

⚠️ Rewrite Risk Acknowledgement

Fresh starts carry the classic risk of losing embedded knowledge. In this case the risk is low: the codebase is small (2K lines), the redesign plan is comprehensive, and the ISPAD-specific logic is intentionally being discarded. The main knowledge to preserve is: PyMuPDF table extraction patterns, checkpoint/resume logic in chunker, and the regex patterns for dosage/recommendation detection.
